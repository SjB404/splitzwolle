# Backend placeholders

Everything on this page is **front-of-house only**: the screen is built, the thing behind it is not.
Nothing here waits for the frontend — each row says where the placeholder lives and what the real
piece has to be. When the collaborator's API lands, this file shrinks; a row that is done gets
deleted, not ticked.

## The account

| What                                                                                                                                                 | Where                                                                                                                    | What the real thing needs                                                                                                                                                          |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/inloggen` and `/inloggen#registreren` are **linked but have no page** — the avatar in the bar and the footer's Account column both land on the 404 | `src/data/navigation.ts` (`LOGIN_PATH`, `REGISTER_PATH`), `src/components/navbar.tsx`, `src/components/footer.tsx` | A login/registration screen. It was designed to sit **outside** `AppLayout` (no bar, no footer — see `docs/DESIGN.md` §6), which is why the route would not be nested in the shell |
| No session, no token, no user — nothing in the app reads who is looking at it                                                                        | —                                                                                                                        | An auth endpoint + a client that stores and sends the credential                                                                                                                   |

## Sharing and saving a route

| What                                                                                                  | Where                                                                                               | What the real thing needs                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The **share button** on the builder's map copies the route's own url — nothing is created server-side | `src/components/routeShareButton.tsx`, `src/data/navigation.ts` (`builderPath`)                | A `POST` that persists the built route (`poiIds` + mode) and answers a short id, so the link survives the places changing and can be counted                                                      |
| A built route survives **only in the url** (`/routes/custom/peperbus,sassenpoort`)                    | `src/data/navigation.ts` (`builderPath`, `parsePlaceIds`), `src/pages/routesPage.tsx` (`useParams`) | Nothing — this is the deliberate stand-in: it is shareable today, the back button works, and it is the shape the API will POST                                                                    |
| A **saved route** lives in this browser (`localStorage["zwolle-routes:saved"]`, ids only)             | `src/data/savedRoutes.ts`, `src/pages/routesPage.tsx` (`useSavedRouteIds`)                          | A saved-routes endpoint behind the account, so the list follows the reader to another device; the module is the single place that changes, and the ids it stores are the ones a `POST` would send |

## Reviews and ratings

| What                                                                                                                                 | Where                                     | What the real thing needs                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The review form accepts a review and **stores nothing** (it prevents the default and stops)                                          | `src/components/routeReviewsPanel.tsx`    | `POST /reviews` with the route id, a score and the text                                                                                                                                           |
| The five reviews are **one sample list shown on every route** — `ROUTE_REVIEWS` is not per route                                     | `src/data/routes.ts`                      | `GET /routes/:id/reviews`, and the list filtered by route                                                                                                                                         |
| The histogram is **invented** from the route's own review count (`buildReviewBreakdown` spreads 100 % over 5★…1★ with a fixed curve) | `src/data/routes.ts`                      | Per-route star counts from the API; the component already takes them as a prop                                                                                                                    |
| `rating`, `reviews`, `durationMinutes`, `elevation`, `distanceKm` on every route are hand-written                                    | `src/data/routes.ts`                      | Distance and duration can come from the Routes API (the line's own `distanceMeters`/`durationMillis` are already read — see `docs/DESIGN.md` §8); the numbers shown on the cards are placeholders |

## Content

| What                                                                                                                       | Where                                                  | What the real thing needs                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |

## Map services

| What                                                                                                                                            | Where                                                                                               | What the real thing needs                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The **Routes API** is refused by the development key, so every planned route is a straight connector with an estimated length × 1.25            | `src/data/googleMaps.ts` (`requestDirections` → `straightRoute`), `src/data/routeGeometry.ts` | Enable _Routes API_ for the key (or fix its referrer restriction). The fallback line stays: it is what a reader sees before the answer arrives, and what remains if the call fails |
| The **Static Maps API** is off by default (`VITE_GOOGLE_MAPS_STATIC_MAPS`), so cards draw a route from its own coordinates instead of a picture | `src/components/mapSnapshot.tsx`, `.env.local`                                                      | Enable _Maps Static API_ and set the flag to `true`                                                                                                                                |
| The maps run on the API's own `DEMO_MAP_ID`, which has a **daily quota** and cannot be styled                                                   | `src/data/googleMaps.ts` (falls back to `DEMO_MAP_ID`)                                        | A cloud Map ID in `VITE_GOOGLE_MAPS_MAP_ID` (see `docs/DESIGN.md` §8)                                                                                                              |

## Not placeholders (so nobody "fixes" them)

- **The theme** in `localStorage["zwolle-routes:theme"]` — that is a deliberate client-side choice, not a session.
- **The picked places in the URL** — shareable on purpose; see above.
- **The saved routes** in `localStorage["zwolle-routes:saved"]` — the reader's own list, with no account to put it in yet.
- **The map fallback panels** — the honest state when a key is missing or a quota is out, not a bug to paper over.
- **The sample reviews' Dutch dates** (`"3 september 2026"`) — written out in the data on purpose; there is no date to format.
